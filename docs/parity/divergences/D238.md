## D238 Extensions relaunch pig in the same process through the Host

What: a Pi extension restarts Pi with another extension set or model scope by spawning a new Pi with `process.execPath`, the same arguments plus its own, stdio `"inherit"`, and exiting with the child's status (AIO's recipe bridge, `recipes/trampoline.ts`). A subprocess extension's argv, stdio and exit are its own process's, so that spawn starts a second pig on the extension's pipes while the first pig waits. Pig adds a host call that ends the current runtime and replaces the pig process image with pig started with the requested arguments and environment:

1. Go `ctx.Relaunch(sdk.RelaunchOptions{Args, Env})`, Rust `ctx.relaunch(&args, &env)`, Python `ctx.relaunch(args, env)`, Lisp `ctx-relaunch ctx args :env env`, and Node `ctx.relaunch({ args, env })` (a Promise). The wire call is `relaunch` with `{"args": string[], "env": {name: string | null}}` and the result is null. `args` is required and is the complete argument list after the pig executable. `env` changes pig's current environment: a string sets a variable and null removes it.
2. When `args` choose no session (`--session`, `--session-id`, `--continue`, `--resume`, `--fork`, `--no-session`) and the current session file exists, pig puts `--session <file>` before them, so the relaunched runtime continues the same session file and session id. A session whose file is not written yet (Pi writes it with the first assistant reply) or that has none is not carried.
3. An accepted relaunch is the mode's shutdown request: interactive mode stops when idle, RPC mode at its shutdown check (D231), and print and JSON mode abort a run in progress, send no further prompt and write no result. A relaunch requested in `session_start` sends no command-line prompt. `session_shutdown` runs with reason `"quit"`, extension processes stop, the TUI restores the terminal, and pig then replaces its image with `execve`: the same PID, terminal, standard streams and process group, and one pig process. Go opens every other descriptor close-on-exec.
4. The host refuses, and the runtime keeps running, with an error the call returns: on Windows, which cannot replace a process image; after pig read non-blank piped stdin, which the relaunched pig could not read again; in RPC mode once pig reads commands from stdin, because the reader's buffered commands would be lost (a relaunch requested while RPC mode starts keeps the reader from reading, and the relaunched pig reads every command the client wrote); while pig shuts down; when a relaunch is pending; and for a `PIG_EXT_*` or `PIG_HARNESS_*` key, an empty key, a key with `=` or NUL, or NUL in an argument or value. A mode that binds no relaunch fails the call with `relaunch is not available in this host`.
5. A termination signal, a crash, or an exit status other than 0 (a later `shutdownWithCode`) ends the process instead, without a relaunch. When `execve` itself fails after the runtime ended, pig writes `pig: relaunch failed: <reason>` to stderr and exits 1.

Not changed: `ctx.shutdown()`, `ctx.ShutdownWithCode`, the RPC and JSON wire formats, and the `session_shutdown` reason values. In JSON mode the relaunched runtime's events follow the first runtime's on the same stdout. The shared environment (D234) is not carried; an extension passes such values in `env`.

Why: AIO's recipes have restart-scoped keys (extensions, models). Under PiG, AIO starts pig through a Node launcher (`bin/aio-pig.mjs`) that applies them before pig starts, because a relaunch from the extension process starts a second pig while the first waits forever. Requested by the task owner for the AIO Go extension (`go/aio/recipes.go`) and its TypeScript original (`recipes/pig-host.ts`).

Owner decision: requested by the task owner. Replacing the process image was chosen over an in-process rebuild with a re-parsed argv: it reuses the startup path unchanged (argument parsing, Piglet selection, settings, terminal setup, environment), gives the relaunched runtime exactly the process a fresh `pig <args>` start gives, and is what Pi's spawn-and-exit does without a second process. Windows refuses the call (no `execve`; a child process there would be the second pig this record removes).
