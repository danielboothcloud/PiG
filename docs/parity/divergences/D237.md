## D237 Extensions write terminal control strings through the Host

What: a Pi extension writes terminal control strings to `process.stdout`, which is the terminal Pi's TUI draws on: an OSC 777 or OSC 99 desktop notification, a window title, BEL. A subprocess extension's stdout is its host wire, and a write to `/dev/tty` from another process can land inside a frame the TUI is drawing, or fail where the process has no controlling terminal. Pig adds a host call that writes the string between TUI frames:

1. Go `ctx.WriteTerminal(data)`, Rust `ctx.write_terminal(data)`, Python `ctx.write_terminal(data)`, Lisp `ctx-write-terminal`, and Node `ctx.ui.writeTerminal(data)` (a Promise). The wire call is `ui.writeTerminal` with `{"data": string}` and the result is null.
2. The interactive UI queues the string on its owner loop, the path `ctx.Bell()` takes, and writes it in one terminal write between two frames. The call returns once the write is queued; it never waits for the TUI loop, so a handler the loop is waiting for cannot deadlock it.
3. The host accepts only strings that neither print nor move the cursor, so the TUI's next frame is drawn on the screen it expects: BEL bytes, OSC strings (`ESC ] ... BEL` or `ESC ] ... ESC \`) whose body has no control bytes, no C1 controls and is not an OSC 8 hyperlink, and tmux passthroughs (`ESC P tmux; ... ESC \`, every inner ESC doubled) of those, at most 64 KiB in total. Anything else (text, CSI, other DCS strings, an unterminated string) is refused whole with an error that names the offending byte, and nothing is written.
4. In print, JSON and RPC mode, which have no terminal UI, the call writes nothing and returns an error that names the mode and what stdout carries there. In interactive mode before the UI is bound, the error says the terminal UI is not running yet.

Not changed: `ctx.Bell()` (it still does nothing and reports no error without a terminal UI), the RPC and JSON mode wire formats, and a Node extension's own `process.stdout`, which stays its host wire.

Why: AIO's notification fallback (`go/internal/notifications`) sends OSC 777, OSC 99 under kitty and the tmux passthrough of either, and wrote them to `/dev/tty`, which fails in some setups and can split a TUI frame. Requested by the task owner for the AIO Go extension.

Owner decision: requested by the task owner; a raw control-string write was chosen over a `TerminalNotify(title, body)` call because AIO builds the OSC 99 and tmux variants itself, and the host validation keeps the TUI frame correct.
